Detects one transaction that takes ACCESS EXCLUSIVE on two or more partitioned parent tables that existed before the change. `DROP TABLE` of a partition and `CREATE TABLE ... PARTITION OF` each lock the partition's parent ([PGM024](https://robert-sjoblom.github.io/pg-migration-lint/rules#pgm024)), and a transaction holds every lock it takes until it ends. Once the transaction has locked the first parent, reads and writes routed through it wait, and they go on waiting while the transaction queues for the next parent's lock behind the traffic already running there. Each further parent adds its wait to the time the earlier ones stay blocked. If one of those locks cannot be taken, because a `lock_timeout` expires or the transaction deadlocks with application traffic that touches two of the parents, the transaction aborts: the work on every parent rolls back, after the earlier parents were blocked for nothing.

The rule looks at each transaction of the migration on its own: the whole file when the migration tool runs it in a transaction, a `BEGIN ... COMMIT` block, or one statement outside a transaction block. `DROP TABLE a, b` is one statement, and so one transaction, that locks the parents of both `a` and `b`. The rule fires once per transaction that locks two or more parents, at the first statement that locks one, and names them all. With `run_in_transaction = false`, golang-migrate's default single `Exec` runs the whole file as one implicit transaction, which the rule does not model, so it misses two parents locked in such a file.

`ATTACH PARTITION` and `DETACH PARTITION` do not count. On a parent the transaction has already locked they add no wait, and `ATTACH` and `DETACH ... CONCURRENTLY` take only SHARE UPDATE EXCLUSIVE on the parent, which lets reads and writes go on. A plain `DETACH PARTITION` does take ACCESS EXCLUSIVE; [PGM004](https://robert-sjoblom.github.io/pg-migration-lint/rules#pgm004) reports it. A parent created in the same change does not count either, as nothing uses it yet.

PGM024 flags the same statements (one finding per parent in the unit): it says that each parent gets locked, this rule that one transaction holds several of those locks at once. PGM024's fix (detach the partition concurrently, then drop it; create the new table standalone, then attach it) avoids the ACCESS EXCLUSIVE lock and so clears both. Where the ACCESS EXCLUSIVE locks are acceptable, change one parent per transaction, so that each lock is held only for that parent's own work. A separate migration per parent is the safest way to get there. Don't split with a `COMMIT` inside a migration the tool already runs in a transaction: runners differ on what runs after it.

**Example** (bad):
```sql
BEGIN;
DROP TABLE measurements_2023;
CREATE TABLE readings_2026 PARTITION OF readings
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
COMMIT;
```

**Fix**: one migration per parent:
```sql
-- V010__drop_measurements_2023.sql
DROP TABLE measurements_2023;

-- V011__create_readings_2026.sql
CREATE TABLE readings_2026 PARTITION OF readings
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
```
