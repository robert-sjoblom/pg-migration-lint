Detects foreign key constraints where the referencing table has no usable index containing any of the FK columns. Without such an index, any query joining or filtering on those columns forces a sequential scan on the referencing table — and so does a referential integrity check when a referenced row is deleted or its key columns are updated.

**Example** (bad):
```sql
ALTER TABLE order_items
  ADD CONSTRAINT fk_order
  FOREIGN KEY (order_id) REFERENCES orders(id);
-- No index on order_items(order_id)
```

**Fix**:
```sql
CREATE INDEX idx_order_items_order_id ON order_items (order_id);
ALTER TABLE order_items
  ADD CONSTRAINT fk_order
  FOREIGN KEY (order_id) REFERENCES orders(id);
```

**Dropping the covering index**: the rule also fires when a migration removes the last usable index covering a foreign key that already exists and stays. That happens with `DROP INDEX` (with or without `CONCURRENTLY`), with `ALTER TABLE ... DROP CONSTRAINT` of a PRIMARY KEY or UNIQUE constraint, whose index goes with it, and with `ALTER TABLE ... DROP COLUMN` of any column of the index, even one the foreign key does not use. A partition's foreign key covered by its parent's index loses that coverage when the parent's index is dropped. Each statement is checked against the schema as it stands just before it, so an index renamed earlier in the same migration is found under its new name: with `ALTER INDEX ... RENAME TO`, with `ALTER TABLE ... RENAME CONSTRAINT` of its PRIMARY KEY or UNIQUE constraint, or with `ADD CONSTRAINT ... USING INDEX`, which gives it the constraint's name. So is an index the migration created.

**Example** (bad):
```sql
-- order_items has FOREIGN KEY (order_id) REFERENCES orders(id),
-- covered only by idx_order_items_order_id.
DROP INDEX CONCURRENTLY idx_order_items_order_id;
```

It does not fire when the same file drops the foreign key too, when another usable index still covers it once the file is done, one the file creates included, when the foreign key had no covering index before the file, as with a temporary index the file creates and drops again, or when the same file adds the foreign key, which the first check already reports once. Nor, while [PGM027](https://robert-sjoblom.github.io/pg-migration-lint/rules#pgm027) is enabled, does it fire on a statement PostgreSQL rejects, such as a `DROP INDEX` that also names the index behind a PRIMARY KEY or UNIQUE constraint: nothing is dropped, and PGM027 reports it. When several statements in a file drop covering indexes of one foreign key, the finding goes to the statement that leaves the key without a covering index, or to the last such statement when the file covers the key again in between.

**Known limitation**: the schema built from the migration history does not record the index PostgreSQL gives each partition for an index on its partitioned parent, so a partition's foreign key counts as covered through the parent's index instead. After `ALTER TABLE ... DETACH PARTITION`, the rule no longer counts the parent's index for the detached table, though PostgreSQL leaves the table its own copy of it. So the rule does not report the detach, nor a drop that leaves the foreign key covered through the parent until a later `DETACH PARTITION` in the same file. Once a partition is detached, dropping its own covering index is reported even when the copy of the parent's index still covers the foreign key.

**Column matching**: FK columns `(a, b)` are covered by any usable index that contains at least one of `a` or `b`, in any position — e.g. `(a, b)`, `(b, a)`, `(a)`, or `(c, b)` all count. An index covering only some of the FK columns still avoids a sequential scan (via a Filter or Recheck), so it counts as coverage even though a fully covering index performs better. Column order does not matter here. The check uses the catalog state after the entire file is processed, so creating the index later in the same file avoids a false positive. A `CREATE INDEX` whose name a table or index in the schema already has creates nothing, as PostgreSQL rejects it ([PGM027](https://robert-sjoblom.github.io/pg-migration-lint/rules#pgm027)), so it does not count.

**Known limitation**: an FK whose only indexed column is low-cardinality (e.g. 10 distinct values over 1M rows) produces no warning, even though the check still degrades to a Bitmap Heap Scan touching a large fraction of the table. Index shape alone can't tell a selective index from an unselective one — the catalog has no column statistics, and requiring the index to also be UNIQUE would not help, since the false-negative case is not unique in the referencing table either.
